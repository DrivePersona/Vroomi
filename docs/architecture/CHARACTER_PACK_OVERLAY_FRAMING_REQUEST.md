# 캐릭터 팩 SDK 요청: 캐릭터별 사각형 오버레이 영역

**기준일:** 2026-11-14 · **대상:** `character-pack-sdk`(비공개) `characterpack-runtime`/`characterpack-content` 0.3.3 이후 · **요청한 쪽:** 앱(이 저장소) · **상태:** 앱·SDK 구현과 에뮬레이터 확인 완료(로컬), SDK 릴리스·매니페스트 반영 대기

## 1. 요약

오버레이 앱 영역은 **캐릭터가 화면에 보이는 부분만**이어야 한다. 지금까지는 모든 캐릭터가 300×400dp 창을 쓰고 그림은 그 안에 10% 안팎의 투명한 여백을 두고 그려져, 창 면적의 상당 부분이 보이지 않는데도 아래 지도의 터치를 막았다. 앱 쪽에서는 창 모양을 줄이는 방법이 없었다(§3).

이번에 정한 방향: **캐릭터마다 창 크기가 다른 사각형**으로, 보이는 범위에 가장자리 여백 8dp를 더한 크기로 한다.

- SDK가 창을 **기준 틀(300×400dp)에서 잘라낸 사각형**으로 그린다. 창이 작아져도 캐릭터 크기는 그대로다(§4).
- 매니페스트 `overlay`에 `offsetXDp`/`offsetYDp`를 더해 창 중심을 틀 중심에서 옮길 수 있게 한다(§4).
- 앱은 2D 프리뷰도 같은 틀에서 잘라 보여 주고, 캐릭터가 바뀌어 창 크기나 위치가 달라지면 창을 새로 만든다(§5).
- 팩별 값은 11개 팩에 대해 정했다(§6). 에뮬레이터에서 창이 팩마다 다르고 보이는 그림과 창 가장자리 사이가 8~10dp임을 확인했다.

**아직 못 한 것:** 에뮬레이터에서 3D 모델이 보이지 않아(§2), 3D 쪽 잘라 그리기는 단위 테스트와 투영 값 로그로만 확인했다. 팩별 값도 2D 프리뷰의 보이는 범위로 정했고 3D 동작 범위(제스처 포함)로는 재지 않았다(§7).

## 2. 실측 정정: 에뮬레이터에서 보이던 것은 2D 프리뷰다

Pleos Connect v2.1.0 AVD(2560×1440, 160dpi, `internalDebug`)에서 확인한 것:

- `CharacterOverlayHost.syncPreview`가 투명한 3D 뷰 **아래**에 `concept.png` 프리뷰(`ImageView`, `FIT_CENTER`)를 둔다. SDK 코드 주석상 "GLB 합성 실패 시의 검증된 미리보기"다.
- 프리뷰를 숨기면 창이 비어 보인다. 원본 SDK 0.3.3에서도 같다. 3D 뷰의 지우기 색을 불투명 마젠타로 바꾸면 창이 마젠타로 채워지므로 표면은 보이지만 모델 픽셀이 없다. 앱은 약 60fps로 그리고 오류 로그는 없으며, 에셋은 로드된다(렌더러블 1개, `idle` 클립). 카메라 절두체를 0.3~1.5배로 바꿔도 화면이 변하지 않았다. `swiftshader_indirect`로도 같았다.
- 미확인 단서: 에셋 `boundingBox`의 반크기가 약 0.007×0.008×0.002로, 메시 좌표(높이 1.55)의 1/100이다(팔 뼈대 노드가 cm 단위로 보임). `transformToUnitCube()`가 스킨드 메시를 잘못 키울 가능성이 있으나 확인하지 못했다.

따라서 이전에 이 문서와 다른 문서에 적었던 "그림이 창의 84%", "창을 줄이면 모델도 같은 비율로 줄어든다"는 **프리뷰의 `FIT_CENTER` 동작**이며 3D 렌더링의 동작이 아니다. 에뮬레이터에서 3D가 왜 안 보이는지, 실제 기기에서는 보이는지는 확인하지 못했다.

## 3. 앱 쪽에서 창 모양을 줄일 수 없던 이유

| 시도 | 결과 |
| --- | --- |
| 캐릭터 창을 터치 비대상(`FLAG_NOT_TOUCHABLE`)으로 두고 안쪽만 덮는 작은 터치 창을 올림 | 창 불투명도가 **0.8에 고정**됐다. 1.0으로 되돌려도 `dumpsys window`가 `alpha=0.8`을 유지했고 캐릭터가 항상 흐려졌다. 원인은 Android 12+의 최대 가림 불투명도(0.8) 규칙으로 보이나 OS 소스로 확인하지는 못했다. 되돌렸다 |
| 터치 가능 영역을 지정하는 공개 API | 확인하지 못했다. 비공개(hidden) API는 쓰지 않는다(앱 마켓 심사·OS 업데이트 위험) |
| 창 크기만 줄임 | 3D는 줄어든 창에 맞춰 다시 그려질 수 있어(§2 때문에 에뮬레이터에서는 확인 못 함) 그림 크기가 함께 변한다. 프리뷰는 `FIT_CENTER`라 함께 줄어든다 |

그래서 창 자체를 보이는 범위에 맞추는 방향을 택했다. 창 안의 투명한 곳이 터치를 받는 것은 그대로지만 그 면적이 줄어든다. 창 바깥 터치가 아래 지도로 전달되는지는 직접 확인하지 못했고 Android의 일반 동작에 따른 추정이다.

## 4. SDK 변경 (`character-pack-sdk` 브랜치 `feat/overlay-stage-crop`, 로컬·미푸시)

- **`CharacterOverlaySpec`** — `offsetXDp`, `offsetYDp`(기본 0)를 더하고 기준 틀 상수 `STAGE_WIDTH_DP = 300`, `STAGE_HEIGHT_DP = 400`을 공개한다. `CharacterManifest`가 오프셋을 읽고 ±150dp 밖이면 거부한다. 기존 값(폭 160~480dp, 높이 220~640dp, 세로형)과 필드가 없을 때의 기본값(300×400)은 그대로다.
- **`StageCrop`**(내부, JVM 테스트 가능) — 기준 틀의 절두체를 알면, 창(틀 중심에서 오프셋만큼 옮긴 사각형)에 해당하는 절두체를 비례로 구한다. 틀과 창의 픽셀 배율이 같아 창 크기가 달라져도 캐릭터 크기가 변하지 않는다.
- **`CharacterSurfaceView`** — 오버레이(투명) 모드에서 `onResized` 뒤에 `Camera.setProjection`으로 잘라낸 절두체를 건다. ModelViewer가 `resetToDefaultState()`에서 기본 투영으로 되돌리므로 그 뒤에도 다시 건다. 일반(불투명) 모드는 그대로다.
- 테스트: SDK 단위 테스트 21개 통과(`StageCropTest` 4개, 매니페스트 오프셋 3개 포함). 에뮬레이터에서 `getProjectionMatrix` 값이 계산과 같음을 로그로 확인했다(200×300 창: `m0` 4.667, `m5` 3.111).

## 5. 앱 변경 (`CharacterOverlayHost`)

- 2D 프리뷰를 **창이 아니라 기준 틀 크기**(300×400dp, 안쪽 여백 15dp)로 그리고, 창 크기와 오프셋만큼 위치를 옮겨 틀의 해당 부분만 보이게 한다. 3D가 같은 틀에서 잘라 그리는 방식과 같아 둘이 어긋나지 않는다. 기본값(300×400, 오프셋 0)에서는 이전과 같다.
- `OverlaySize`에 오프셋을 넣어, 크기나 오프셋이 다른 캐릭터로 바뀌면 기존 경로대로 창을 새로 만든다(Filament 창을 재사용하면 검은 사각형이 되는 문제를 피하는 경로).
- 이 변경은 오프셋 필드가 있는 SDK(0.3.9 이후)에서만 컴파일된다. 앱의 `drivepersona.characterpack.version`은 SDK 릴리스 뒤에 올린다.

## 6. 팩별 오버레이 값

방법: 각 `concept.png`에서 알파 16 초과 픽셀의 범위를 구하고, 프리뷰가 기준 틀에 `FIT_CENTER`로 놓이는 위치(그림 영역 270×370dp)로 환산한 뒤 사방에 8dp를 더했다. 폭·높이는 매니페스트 허용 범위(160~480 × 220~640)에 들어 모두 그대로 쓸 수 있었다. 오프셋은 사각형 중심에서 틀 중심(150, 200)을 뺀 값이다. `dev.mori`는 `concept.png`가 없어 이 방법을 쓸 수 없으므로 지정하지 않는다(기본 300×400).

실측은 에뮬레이터(160dpi라 1dp = 1px)에서 창 프레임(`dumpsys window`)과 창 안의 그림 bbox(배경과 24 이상 다른 픽셀)로 했다.

| 팩 `ai.meshy.` | 폭×높이(dp) | 오프셋 x, y | 300×400 대비 창 면적 | 실측 여백 좌/상/우/하(px) |
| --- | --- | --- | --- | --- |
| `chuuni` | 254×355 | +0, +6 | 75% | 9/10/9/8 |
| `dojikko` | 250×342 | +0, +13 | 71% | 8/8/8/9 |
| `fox` | 277×322 | +0, +9 | 74% | 9/8/8/8 |
| `knight` | 266×309 | +8, +2 | 68% | 8/8/9/9 |
| `kuudere-os` | 256×348 | +0, +4 | 74% | 9/9/9/9 |
| `magical` | 241×284 | -2, +6 | 57% | 8/9/8/9 |
| `mechanic` | 278×338 | +0, +6 | 78% | 8/8/8/9 |
| `onee` | 242×344 | +0, +11 | 69% | 8/8/8/8 |
| `onii` | 238×330 | +0, +13 | 65% | 8/8/8/9 |

평균 창 면적은 기존의 약 72%다. 줄어든 면적은 가장 작은 `magical`이 43%, 가장 큰 `tsundere`가 18%다.

같은 확인에서 정리한 동작: 길게 눌러 열리는 플로팅 메뉴가 좁아진 창 옆에 정상 위치에 뜨고, "캐릭터 바꾸기" 시트에서 다른 크기의 캐릭터로 바꾸면 창이 새 크기(예: 266×332 → 254×355)로 다시 만들어지며 검은 사각형은 보이지 않았다.

## 7. 알려진 한계와 SDK에 요청할 것

한계:
- **3D 동작 범위는 재지 않았다.** 값은 정지 프리뷰(`concept.png`, T자 자세)의 보이는 범위로 정했다. 3D 모델의 idle·GREETING·TOUCH·차량 이벤트 제스처에서 팔·망토가 이 사각형 밖으로 나가는지는 모른다. 이슈 #11의 수용 기준("안전 여백 안에서 팔·망토·소품이 잘리지 않아야 한다")을 지키려면 실제 모델 렌더에서 클립별 합집합을 재서 값을 조정해야 한다.
- 3D 뷰의 10% 안전 여백(`VIEWPORT_SAFE_SCALE = 0.90`)과 프리뷰(여백 5%)가 같은 크기로 겹치는지는 모른다. 실제 기기에서 3D와 프리뷰가 함께 보이면 두 그림의 크기 차이가 드러날 수 있다.
- 사각형 안의 투명한 곳(어깨 옆·다리 사이 등)은 여전히 터치를 받는다. 면적이 줄었을 뿐 모양이 실루엣은 아니다(사각형을 우선하기로 했다).
- 창 크기·위치가 팩마다 달라, 저장된 창 위치(왼쪽 위 기준)에서 캐릭터를 바꾸면 그림이 몇 dp 옮겨 보인다. 위치 보정은 하지 않았다.

SDK에 요청:
1. `offsetXDp`/`offsetYDp`와 잘라 그리기(§4)를 받아 릴리스하고, 11개 팩의 `overlay`를 §6 값으로 반영한다(값은 임시이며 3. 이후 확정).
2. 에뮬레이터에서 3D 모델이 그려지지 않는 이유를 확인한다(§2의 `boundingBox` 단위 단서 포함). 실제 기기와 AVD 모두에서 3D가 보이는 상태에서 `transformToUnitCube()` 결과를 확인한다.
3. 3D가 보이는 환경에서 모든 클립의 렌더 범위 합집합을 재서 `overlay` 값을 확정한다. 새 클립이 추가될 때마다 다시 잰다.
4. 선택: 렌더 범위 조회(`CharacterPack.renderBounds`, 앱이 플로팅 메뉴 기준 위치로 쓴다)와 모델 위 판정(`isOnModel`, Filament `View.pick`). 지도 터치 통과는 되지 않으며 아바타 반응만 줄이는 보조 수단이다.
